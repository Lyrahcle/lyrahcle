# Evidence provenance and confidence

Lyrahcle must distinguish observations from context and inference. A prominent severity label never changes the epistemic status of the underlying evidence.

## Operator-facing evidence kinds

| Kind | Meaning |
|---|---|
| Live | Captured by an enrolled physical agent during the current session |
| External | Synchronized from a named third-party source such as NVD or Celestrak |
| Simulated | Generated by a synthetic source for development or demonstration |
| Replayed | Derived from a stored capture and sent through the analysis pipeline again |
| Inferred | Calculated by Lyrahcle from other evidence, for example an SGP4 position |
| Confirmed | Supported by an exact, independently verifiable match |
| Context only | Useful for investigation but not proof of exposure or compromise |

## CVE-to-asset boundary

The current matcher maps NVD search keywords to broad asset kinds. It does not have vendor, product, version, CPE, PURL or SBOM inventory. Every association created by this matcher therefore uses:

- `applicability_status=unknown`
- `match_method=thematic_asset_kind`
- `confidence=20`
- `context_only=true`

Context-only alerts remain visible and acknowledgeable, but they do not contribute exposure points to satellite or mission risk. A future inventory-aware matcher may set `context_only=false` only after it can explain a product/version match. Only `probable_exposure` and `confirmed` non-contextual alerts influence exposure risk.

## Orbital boundary

Satellite positions are SGP4-derived inferences. They are not direct spacecraft telemetry. The API returns `position_evidence_kind=inferred`. Until TLE source identity is persisted, `tle_source=celestrak_or_operator` explicitly preserves that ambiguity.
